# Eval run-history persistence — design (2026-07-23)

## Motivation

`pnpm eval` / `pnpm eval:real-world` print accuracy numbers to the console and nothing else.
Today, "did we actually improve" is tracked informally in commit messages (e.g. commit `96d9569`:
"brandName 22->25, classType 26->30..."), which means:

- Comparing across more than two points in time means reading git log prose and doing mental math.
- There's no per-provider (`mock` / `local-ocr` / `gemini` / `claude` / `openai`) or per-set
  (`default` / `real-world`) history — only whatever happens to be in the most recent commit
  message.
- The detailed "which image failed on which field, with what value" breakdown (used ad hoc during
  this session's investigation into the Phase 2 field-selection candidates) isn't captured anywhere
  — it has to be regenerated by hand each time.

This spec adds structured, queryable persistence for both, so future work (starting with the
Phase 2 field-selection fixes queued up right after this) can be verified against recorded deltas
instead of manually copy-pasted console output.

## Goals

- Every `pnpm eval` / `pnpm eval:real-world` invocation automatically appends a summary record to a
  committed, append-only history log — no flag to remember.
- The summary log captures enough to answer "are we improving": timestamp, git commit (+ dirty
  flag), provider, set, overall accuracy, per-field accuracy, violations-caught rate.
- A separate, gitignored, per-(set, provider) detail file captures full per-item/per-field
  actual-vs-expected-vs-extracted data for the most recent run — replaces ad hoc re-instrumentation.
- A new `pnpm eval:history` command prints recent history log entries as a readable table, so the
  trend is visible without hand-reading JSONL.
- Zero changes to matching/extraction behavior or existing eval console output — this is additive
  observability tooling only.

## Non-goals

- No automatic regression gate beyond the existing one (`pnpm eval` mock/default must stay 100%,
  enforced today via `process.exit(1)` in `eval/run.ts`). This spec does not add a new CI gate on
  the real-world numbers — they remain observability, not a pass/fail check (consistent with the
  Phase 1 spec's stated posture).
- No diffing/comparison tool (e.g. `pnpm eval:diff run1 run2`) in this pass — `pnpm eval:history`'s
  readable table is enough to eyeball a trend; a dedicated diff tool is a follow-up if the table
  proves insufficient.
- No pruning/rotation of `eval/history.jsonl` — at one line per run this would take years to become
  a real size concern; not worth the complexity now.
- This does not touch `app/`, `/api/verify`, or any production code path — it's dev/eval tooling
  only, and doesn't interact with invariant 6 ("persist nothing") in `CLAUDE.md`, which governs the
  deployed app's handling of user-submitted labels/application data, not committed eval fixtures.

## Design

### File formats and locations

**`eval/history.jsonl`** (new, committed to git) — append-only, one JSON object per line:

```json
{
  "timestamp": "2026-07-23T19:42:11.000Z",
  "gitSha": "8fdbd8a...",
  "dirty": false,
  "provider": "local-ocr",
  "set": "real-world",
  "entries": 46,
  "overallCorrect": 16,
  "overallTotal": 46,
  "perField": {
    "brandName": { "correct": 26, "total": 46 },
    "classType": { "correct": 30, "total": 46 }
  },
  "violationsCaught": 5,
  "violationsTotal": 5,
  "extractionErrors": 0
}
```

`provider` is the actual provider name returned by `providerByName()` (`mock` | `local-ocr` |
`gemini` | `claude` | `openai`), not a generic "cloud" bucket — this distinguishes which cloud
model a run used. `gitSha`/`dirty` come from shelling out to `git rev-parse HEAD` and
`git status --porcelain`, wrapped in try/catch so a non-git environment (or `git` not on `PATH`)
degrades to `gitSha: null` instead of crashing the eval run.

**`eval/.results/<set>-<provider>.json`** (new directory, gitignored) — overwritten (not appended)
on every run for that exact `(set, provider)` pair. Contains the full per-item, per-field detail:

```json
[
  {
    "file": "spirits-old-tub-bourbon-front.jpg",
    "field": "brandName",
    "actual": "MISMATCH",
    "expectedOneOf": ["MATCH", "REVIEW"],
    "ok": false,
    "extractedValue": "KENTUCKY STRAIGHT",
    "appValue": "OLD TUB"
  }
]
```

Plus one row per item for the overall verdict (`field: "__overall__"`) and violation-catch result
(`field: "__violation__"`), so the whole per-item picture is in one file per (set, provider).

### `eval/run.ts` changes

The main loop currently only accumulates aggregate counters (`overallCorrect`, `fieldStats` map).
It needs to also push a detail row per field check (and per item's overall/violation result) into
an array, then hand both the aggregate stats and the detail array to `recordRun()` after the loop,
before the existing `process.exit(0)`. Console output (the `✓`/`✗` lines and the summary printed at
the end) is unchanged — recording is purely additive, called once, after everything that already
happens today.

### `eval/record-run.ts` (new)

A single exported function, `recordRun(runData: RunRecord, paths?: { historyPath?: string;
resultsDir?: string }): Promise<void>`, doing exactly the two writes above (append to
`eval/history.jsonl`, overwrite `eval/.results/<set>-<provider>.json`) plus the git-metadata lookup.
`paths` defaults to the real committed locations but lets tests inject a temp directory instead —
this is what keeps the unit tests (below) from appending to or clobbering the real, committed
`eval/history.jsonl` on every test run. Kept as its own module (not inlined into `run.ts`) so it has
one clear purpose, is independently testable, and keeps `run.ts` focused on running the eval rather
than also owning file I/O and git-shelling concerns.

### `eval/print-history.ts` (new) → `pnpm eval:history`

Reads `eval/history.jsonl`, optionally filtered by `--set` and `--provider` CLI flags, and prints
the last N (default 20) matching entries as a table: timestamp, short SHA (+ `*` if dirty),
provider, set, overall %, per-field %, violations %. Read-only — never writes.

### `package.json` / `.gitignore`

- New script: `"eval:history": "tsx eval/print-history.ts"`.
- New `.gitignore` entry: `/eval/.results/`, grouped with the existing "Playwright MCP / local
  verification artifacts" section since it's the same category (generated, local, derived).

## Testing

- Unit tests for `eval/record-run.ts`, using injected temp-directory `paths` (never the real
  committed `eval/history.jsonl`): appends a well-formed line; overwrites (not appends) the detail
  file on a second call for the same (set, provider); degrades gracefully (`gitSha: null`,
  `dirty: null`) when git commands fail.
- Unit tests for `eval/print-history.ts`: filters correctly by `--set`/`--provider`; handles an
  empty or missing `history.jsonl` without crashing.
- Manual verification: run `pnpm eval` and `pnpm eval:real-world` once each, confirm
  `eval/history.jsonl` gains exactly one well-formed line per run, confirm
  `eval/.results/default-mock.json` and `eval/.results/real-world-local-ocr.json` are created and
  gitignored (`git status` shows nothing new under `eval/.results/`), confirm `pnpm eval:history`
  prints both runs correctly.

## File inventory

New:

- `eval/record-run.ts`, `eval/record-run.test.ts`
- `eval/print-history.ts`, `eval/print-history.test.ts`
- `eval/history.jsonl` (committed, starts with whatever the first real run produces)

Modified:

- `eval/run.ts` (collect per-item detail array; call `recordRun()` before exit)
- `package.json` (`eval:history` script)
- `.gitignore` (`/eval/.results/`)

Unchanged:

- `lib/vision/*`, `lib/matching/*`, `lib/ttb/*`, `eval/expected.json`, `eval/expected-real-world.json`,
  everything under `app/`.

## Risks / open notes

- Git-shelling from a test-runner/eval script is a new pattern in this codebase; kept narrowly
  scoped (two read-only, try/caught commands) rather than a general git-utility module, since that's
  all this needs.
- `eval/history.jsonl` will accumulate one line per local run, including exploratory ones (e.g. a
  developer running `pnpm eval:real-world` five times while debugging one fix). That's accepted
  noise — the log is meant to be skimmed via `pnpm eval:history`, not read raw, and per-run
  timestamps make exploratory clusters easy to recognize.
- Relationship to the Phase 2 field-selection work: this spec is a prerequisite, built and landed
  first. The Phase 2 plan's per-task verification step ("run eval, report delta") will use
  `pnpm eval:history` instead of manually recording numbers in commit messages.
