## 1. `loadSample` silently swallows fetch errors

- **Where:** `app/page.tsx:117-126`
- **Severity:** Medium
- **What:** `loadSample` calls `reset()`, then `await fetch(...)` and `await res.blob()` with no error handling. If the fetch fails (network error, 404, 500), the user sees nothing happen — no file is set, no error is shown. A non-OK response also produces a `File` containing HTML error body, which then fails MIME sniffing in the API route with a confusing message.
- **Impact:** Broken UX. The sample button appears to do nothing.
- **Fix:** Wrap the fetch in try/catch and surface an error to the user (e.g. via the existing `error` state in `useVerify`, or a new local error state). Also check `res.ok` before calling `res.blob()`.

## 2. `Content-Length` header omission bypasses size pre-check

- **Where:** `app/api/verify/route.ts:53-56`
- **Severity:** Medium
- **What:** A client can omit the `Content-Length` header (chunked transfer encoding). `Number(req.headers.get("content-length"))` returns `NaN`, `Number.isFinite(NaN)` is `false`, and the size guard is skipped. The full body is then buffered by `req.formData()` without bound — relevant for self-hosted deploys where Vercel's ~4.5 MB platform cap does not apply.
- **Impact:** On self-hosted deploys, an attacker can send an arbitrarily large multipart body without hitting the pre-check, consuming memory until the `image.size` check or the OS OOM-kills the process.
- **Fix:** When `Content-Length` is absent and `NODE_ENV !== "development"`, reject with 413. Alternatively, enforce a streaming body-size limit via middleware.

## 3. Duplicate React keys in warning lists

- **Where:** `components/verdict-card.tsx:52`, `app/batch/page.tsx:91`
- **Severity:** Low
- **What:** `<li key={w}>` uses the warning text as the React key. If two warnings are identical strings, React logs a console warning and can mis-render the list. Currently all warning texts are distinct, but this is fragile — a future refactor could easily produce duplicates.
- **Impact:** Console warnings and potential rendering glitches.
- **Fix:** Use a stable, unique key per warning (e.g. index into the warnings array, or a generated ID).

## 4. `escapeCsvCell` doesn't cover all formula-injection prefixes

- **Where:** `lib/csv.ts:90`
- **Severity:** Low
- **What:** The regex `/^[=+\-@\t]/.test(v)` catches `= + - @ \t` but not backtick `` ` `` or pipe `|`, which some spreadsheet apps interpret as formula triggers. The function's own comment references formula injection but the guard is incomplete.
- **Impact:** Theoretical CSV injection if a filename or field value starts with `` ` `` or `|`. Current input space makes this unlikely in practice.
- **Fix:** Extend the regex to `/^[=+\-@\t`|]/.test(v)`.

## 5. `normalizeLoose` silently drops non-ASCII characters not in the fold map

- **Where:** `lib/ttb/normalize.ts:27`
- **Severity:** Low
- **What:** After NFKD decomposition and diacritic stripping, `/[^a-z0-9\s]/g` removes any remaining non-ASCII. Characters in the explicit `FOLD` map (æ, œ, ø, ß, þ, ð, ł, đ, ħ) are handled, but other characters (e.g., `å`, `ü`, `ç` after decomposition) are stripped. Two brand names differing only by such a character normalize identically and match.
- **Impact:** False MATCH verdicts for imported spirits with accented characters in brand names that are not in the fold map.
- **Fix:** Either extend the fold map to cover the remaining characters likely to appear on TTB labels, or document this as an accepted trade-off.

## 6. Batch images input persists across CSV re-uploads

- **Where:** `app/batch/page.tsx:62-68`
- **Severity:** Low (UX)
- **What:** When the user uploads a new CSV, `rows` and `csvErrors` are updated, but the `files` state (from the images `<input>`) is not reset. Old images from a previous selection remain matched (or unmatched) against the new CSV rows.
- **Impact:** Confusing UX — stale images can appear matched to new CSV rows, or produce "unmatched images" warnings for files the user thought they cleared.
- **Fix:** Clear the `files` state (and reset the images input ref) when a new CSV is uploaded.

## Non-bugs worth noting

These are not defects but are worth recording for future reference.

### `detailsId` uses sorted-array index, not a stable ID

- **Where:** `components/batch-table.tsx:72`
- **What:** `const detailsId = \`batch-details-${i}\``uses the index`i`from the sorted array. When the sort order changes, the numeric suffix changes for the same row. The`aria-controls`/`id`linkage is correct within a single render, and`openRow` tracks by filename, so nothing breaks. But if the batch table ever needs to support multiple open rows or persistent expand state across re-renders, this would need a stable key.

### Cloud providers instantiate new SDK clients per request

- **Where:** `lib/vision/cloud/claude.ts:10`, `lib/vision/cloud/openai.ts:8`, `lib/vision/cloud/gemini.ts:8`
- **What:** Each `extract` call creates a new `Anthropic()`, `OpenAI()`, or `GoogleGenerativeAI()` instance. The SDKs likely cache HTTP connections internally, so this is not a correctness issue, but it is wasteful. On high-throughput batch runs, consider hoisting the client to module scope.

### Singleton tesseract worker is never terminated

- **Where:** `lib/vision/local-ocr.ts:31`
- **What:** The worker is created on first use and cached in `workerPromise` indefinitely. On Vercel serverless, function instances are recycled, so this is fine. On long-running self-hosted deploys, the worker stays in memory for the process lifetime. This is by design (re-initializing the worker is expensive), but worth noting if memory profiling ever becomes necessary.
